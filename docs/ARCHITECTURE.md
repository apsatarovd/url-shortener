## 1. Подходы к генерации короткого кода

### Хеш от URL
**Как работает:**
Берём длинный URL, считаем хеш (MD5 или SHA-256), кодируем в base62 и обрезаем до 7 символов.

**Плюсы:**
- Одинаковый URL всегда даёт одинаковый код. 

**Минусы:**
- **Коллизии.** Разные URL могут дать одинаковый хеш после обрезки.
- **Обработка коллизий сложная**: "хешировать заново" нельзя (получим тот же код). Можно добавить случайную "соль" к URL перед хешированием, но это убивает повторяемость  — один и тот же URL начнёт давать разные коды, и главный плюс подхода перестанет работать
- **Дополнительные запросы к БД** для проверки уникальности.

### Счётчик + Base62

**Как работает:**
Создаём запись в БД, получаем `id` (1, 2, 3...). Кодируем `id` в Base62: `1 - "1"`, `62 - "10"`, `1000 - "g8"`.

**Плюсы:**
- Коллизий нет.
- Не нужна проверка в базе.
- Просто реализовать.

**Минусы:**
- **Синхронизация между серверами.** Если серверов несколько, они могут выдать один и тот же номер. Нужен центральный счётчик или сложная логика.
- - **Предсказуемость.** Коды идут подряд: `1`, `2`, `3`... Видно, сколько ссылок в системе. Злоумышленник может перебрать все ссылки.

### Случайный код

**Как работает:**
Генерируем случайную строку из 6–8 символов (a-z, A-Z, 0-9).
Проверяем в базе — если такой код уже есть, генерируем заново.

**Плюсы:**
- Просто реализовать.
- Коды непредсказуемые.
- Каждая ссылка получает свой код.

**Минусы:**
- Каждый раз надо проверять в базе — лишний запрос.
- Возможны коллизии (редко).
- Одинаковый URL - разные коды.

### Snowflake ID 

**Как работает:**
Генерируем 64-битный ID из разных секций: время (41 бит) + ID сервера (10 бит) + счётчик (12 бит).

**Плюсы:**
- Уникален в распределённой системе (несколько серверов).
- Не нужна центральная БД для счётчика.
- ID сортируются по времени создания.

**Минусы:**
- **Сложно реализовать.**
- Зависит от синхронизации времени между серверами.
- Для одного сервера — избыточно.
- ID получается длинным (~11 символов в Base62)

### Hashids (на основе ID из БД)

**Как работает:**
Создаём запись в БД, получаем `id` (1, 2, 3...).
Прогоняем `id` через библиотеку Hashids с секретной солью - получаем код вида `k3M`.

**Плюсы:**
- Коллизий нет — id уникален.
- Не нужна проверка в базе.
- Коды выглядят случайными, а не последовательными.
- Готовая библиотека.

**Минусы:**
- Это не шифрование. Если соль утечёт — коды можно декодировать обратно в id.
- **Те же проблемы с масштабированием, что у счётчика**: нужен центральный источник ID (БД), несколько серверов не смогут работать независимо.
- Соль нужно где-то хранить и защищать 



## 2. Оценка нагрузки

### Сколько пользователей

- 100 000 человек в день
- Каждый создаёт 10 ссылок → **1 млн ссылок в день**
- Каждую ссылку кликают 50 раз → **50 млн кликов в день**

### Запросы в секунду

В сутках 86 400 секунд.

| Операция | Средняя нагрузка | Пик (вечером) |
|---|---|---|
| Создание ссылок | ~12 в секунду | ~50 в секунду |
| Клики (редиректы) | ~580 в секунду | ~2 300 в секунду |

### Данные за год

- Ссылки: **~100 ГБ**
- Клики: **~6 ТБ**

### Что это значит

- **Redis обязателен** — без него 2 300 кликов в секунду не выдержать.
- **Клики за год займут 6 ТБ** — старые надо будет удалять или агрегировать.
- **Сервисы можно масштабировать** — добавлять копии `link-service` и `analytics-service` без изменения архитектуры.

### Как проверим после реализации

Когда проект будет готов, запустим нагрузочный тест (`wrk`). Сравним реальные цифры с оценкой. Результаты запишем сюда.
